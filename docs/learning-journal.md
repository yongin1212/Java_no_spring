# 순수 Java HTTP 서버 및 미니 DI·MVC 학습 기록

최초 정리: 2026-11-10 (KST). 아래는 현재 채팅에 제공된 과거 대화의 회고 기록이다. 개별 질문의 정확한 발생 시각은 복원하지 않았다.

## 목표와 학습 방식

- 목표: 순수 Java로 작은 HTTP 서버와 IoC·DI·MVC를 구현하며 Spring 구조와 Java 기초를 이해하고 포트폴리오에 설명한다.
- 게시글 CRUD·좌석 예약 서비스 아이디어에서, 프레임워크 자체의 원리 구현으로 목표를 변경했다.
- 사용자가 예제를 직접 따라 쓰고 주석으로 개념을 연결한다. AI는 예제·힌트·리뷰를 제공한다.
- 예제 참고 학습을 독자 설계·구현으로 과장하지 않는다. 이후 스스로 바꾼 설계와 검증 결과를 별도 기록한다.

## 현재 상태와 다음 단계

- 대화에서 다룬 것: 소켓 연결 수락, 요청 첫 줄·헤더 읽기, HTTP 응답 작성, 200/400/404 분기, 반복 연결 처리.
- 최근 제공된 예제: main / handleRequest / sendResponse 메서드로 역할 분리. 사용자의 적용·실행 성공은 미확인.
- 2026-11-10 파일 확인: src/Main.java에 소켓 서버 코드와 port = 9990이 있다. 전체 컴파일·실행 검증은 하지 않았다. 예제의 8080과 실제 코드 포트를 혼동하지 말 것.
- 다음: 메서드 분리 구조 이해·동작 확인 후, 객체 등록·생성·조회 컨테이너 → 생성자 DI → 어노테이션 요청 매핑.
- IoC·DI·MVC 구현 완료나 포트폴리오 성과로 아직 주장할 수 없다.

## 어려움과 고민

### 1. Tomcat 없이 서버가 열리는 이유
- 질문: “톰캣이 없는데 웹서버를 어떻게 열어?”
- 혼란: Tomcat이 있어야만 HTTP 통신이 가능하다고 생각했다.
- 설명: Java 소켓 API와 운영체제 네트워크 기능으로 연결을 받고 HTTP 형식의 응답을 직접 작성할 수 있다. 이는 Tomcat 기능의 아주 작은 일부에 대응한다.
- 확인 상태: 설명 제공. 독립적인 설명·실행 검증은 추가 필요.

### 2. HTTP·TCP·Spring의 관계와 학습 목적
- 질문: “HTTP랑 Spring이 무슨 관련인데?”, “내가 뭘 하고 있는지도 모르겠어.”
- 원인: 네트워크·서버·프레임워크 개념을 동시에 설명하며 목표와 현재 단계가 흐려졌다. 설명 방식도 혼란에 기여했다.
- 정리: 현재 HTTP/1.1 서버는 TCP를 통해 요청·응답을 전달한다. 요청을 받고 해석하는 입구를 만든 다음, 경로에 맞는 Java 메서드를 호출하는 MVC로 연결한다. IoC·DI는 HTTP 없이도 구현 가능하다.
- 사용자 확인: “이게 웹서버고 HTTP 통신을 TCP로 하며 이는 Spring MVC를 만들기 위한 과정”으로 재정리했다.
- 남은 검증: HTTP 서버 영역과 IoC·DI·MVC 영역을 스스로 구분해 설명하기.

### 3. ServerSocket·Socket·accept 구분
- 질문: “왜 따로 받아?”, “accept가 연결을 어떻게 받아?”
- 어려움: 연결 대기용 객체와 연결별 통신용 객체가 분리되는 이유.
- 설명: 운영체제가 TCP 연결을 처리하고, accept는 수락된 연결을 나타내는 Socket을 반환한다. ServerSocket은 새 연결을 기다리고, 각 Socket은 특정 TCP 연결로 데이터를 읽고 쓴다.
- 사용자 확인: “서버소켓을 통해 받고 그것들마다 하나씩 소켓을 배정해서 서버 코드 내에서 객체로 사용하는 거야?”라고 재정리했다.
- 주의: 브라우저 하나당 소켓 하나가 아니라 TCP 연결 하나당 소켓이라는 기준을 유지한다.

### 4. requestLine과 headerLine이 다른 이유
- 질문: “같은 값 아니야? 왜 두 개로 나눠?”
- 설명: 같은 reader라도 readLine을 호출할 때마다 다음 줄을 읽는다. 첫 줄은 요청 메서드·요청 대상·버전이고, 이후 줄은 헤더다. 빈 줄은 헤더 종료, null은 입력 종료다.
- 남은 검증: 실제 요청 로그에서 첫 줄·헤더·빈 줄을 구분하기.

### 5. split과 요청 형식 검사
- 질문: “왜 requestParts가 3 이상이 아니면 400이야?”
- 설명: 조건은 3 이상이 아니라 정확히 3개인지 검사한다. 요청 첫 줄을 공백으로 나눠 메서드·요청 대상·버전에 접근한다.
- 사용자 확인: “3개의 부분으로 나눠져 있으니까 split을 한 거구나.”
- 한계: 단순 split과 원소 수 검사는 완전한 HTTP 파서가 아니다. 메서드·버전·요청 대상의 유효성 검증은 별도다.

### 6. 상태 코드가 결정되는 위치
- 질문: “다른 상태 코드가 뜨면?”, “상태마다 만들어야 하나?”
- 어려움: HTTP 상태가 자동으로 발생하는지, 응답 코드를 상태마다 복제해야 하는지 혼란.
- 설명: 서버가 처리 결과에 맞춰 상태·설명·본문을 결정하고 공통 응답 작성부에서 전송한다. 예외가 발생해도 자동으로 500 응답이 되지 않는다.
- 현재 예제 범위: 200/400/404. 405, 예외의 응답 변환 등은 아직 구현·검증하지 않았다.

### 7. 무한 반복과 메모리
- 질문: “메모리가 부족해서 죽는 거 아니야?”
- 설명: 반복 자체가 누적 저장을 의미하지 않는다. try-with-resources가 소켓을 닫고, 참조가 사라진 객체는 GC 회수 대상이 된다. accept는 대기하므로 바쁜 반복이 아니다.
- 남은 위험: 길이 제한 없는 readLine, 읽기 제한 시간 부재, 단일 연결의 지연이 다음 연결을 막는 구조. 해결 완료로 기록하지 않는다.

### 8. 리스너·커넥션 풀·스레드 풀 용어 혼란
- 상황: 선생님이 언급한 리스너·커넥션 풀의 장점과 헤더 로그의 관계를 질문했다.
- 설명 정정: 헤더 로그는 읽은 요청을 출력해서 볼 수 있으며 풀이 필수는 아니다. 연결 재사용을 위한 커넥션 풀과 작업 스레드를 재사용하는 스레드 풀은 구별해야 한다.
- 미해결: 선생님이 말한 커넥션 풀이 관리하는 연결의 종류·의도는 자료가 없어 확인되지 않았다. 선생님이 스레드 풀을 뜻했다고 단정하지 않는다.
- 진행 결정: 풀 구현은 보류하고 현재 서버 흐름과 객체 컨테이너 학습을 우선한다.

### 9. 주석과 실제 동작 연결
- 상황: 사용자가 개념 목록을 따라 주석을 작성했으나 AI가 위치를 오류처럼 설명해 혼란을 줬다.
- 실제 코드 수정 사항: Content-Lenght → Content-Length 헤더 철자 오류를 안내했다. 사용자 파일에서 수정·동작 확인은 별도 필요.
- 개념 정정: flush는 자원 해제가 아니다. try-with-resources가 종료 시 close를 호출한다. InputStreamReader는 디코딩, BufferedReader는 문자 버퍼링을 담당한다.
- 학습 방식 결정: 기존 전체 코드에 정확한 주석을 붙이고 Java 문법·API·HTTP 규칙을 구분해서 설명한다.

## 포트폴리오로 발전시킬 확인 과제

- 요청 로그와 응답 상태를 캡처해 실제 동작 증거 남기기.
- 메서드 분리 전후에 책임과 데이터 전달 흐름을 직접 설명하기.
- 제한 시간·요청 크기 제한·동시 처리 중 실제 선택한 과제만 재현 → 수정 → 검증 과정 기록하기.
- IoC·DI 구현 시 객체 생성 순서·객체 공유 범위·순환 의존성의 설계 근거 기록하기.
- 현재 기록은 학습 중의 질문과 설명이다. 검증된 장애 해결이나 성능 개선 실적으로 바꾸어 쓰지 않는다.

## 챕터별 학습 기록

### 2026-11-10 — HTTP 처리 메서드 분리와 리팩토링
- 구현 내용: 사용자가 main, handleRequest, sendResponse로 분리한 코드를 채팅에 제출했다. main은 연결 수락·반복·소켓 종료, handleRequest는 요청 읽기·경로 판단, sendResponse는 HTTP 응답 생성·전송을 담당한다.
- 대표 질문: “이건 그냥 진짜 분리만 한 거네? 근데 분리하면 뭐가 좋냐.”
- 고민: 동작이 같다면 메서드를 나누는 작업이 어떤 가치를 갖는지 궁금했다.
- 학습 내용: 역할을 나누면 수정할 위치를 찾기 쉽고 변경 범위가 줄어든다. 상태 코드별 응답에서 공통 전송 로직을 재사용하면 헤더 변경도 한 곳에서 할 수 있다. 동작을 유지하며 구조를 개선하는 작업이 리팩토링이라는 점을 배웠다.
- 회고용 요약: “처음에는 메서드 분리가 단순히 코드를 옮기는 작업이라고 생각했다. 연결 관리·요청 처리·응답 전송을 나누며, 분리의 목적이 역할을 명확히 하고 변경할 부분을 좁히며 중복을 줄이는 데 있다는 것을 배웠다.”
- 확인 근거: 제출된 코드에서 역할 분리와 200/400/404 응답의 공통 sendResponse 호출을 확인했다. 실행 성공·회귀 검증이나 유지보수 효과의 실측은 아직 확인하지 않았다.
- 리뷰 사항: 포트 주석의 8080을 실제 값인 9990에 맞추고, 광범위한 Exception 대신 현재 예상하는 IOException을 잡도록 권장했다. 반영 여부는 미확인이다.
- 다음 확인: /hello의 200 응답, 다른 경로의 404 응답, 반복 접속 동작을 확인한 뒤 객체 컨테이너 학습으로 진행한다.
